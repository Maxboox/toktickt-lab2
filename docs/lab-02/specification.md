# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
This sprint delivers the Requester-facing interface for the IT support ticket system. Requesters can create tickets, view their tickets, manage attachments, and track their support requests.

---

## 2. Stakeholder Request Interpretation
The IT department requires a professional application for users to submit support requests. Users must describe problems, select categories and related systems, indicate priority levels, attach supporting evidence, and submit tickets. After submission, users must be able to locate their tickets, search and filter them, open ticket details, and manage attachments. The system must generate official ticket numbers, store data safely, and prevent one requester from viewing another requester's tickets. Since authentication will be introduced in the next sprint, a temporary Development Requester selection screen is provided for testing purposes.

---

## 3. Scope

### Included
- Development Requester selection screen (testing only)
- Ticket creation with validation
- "My Tickets" list with search, filters, sorting, and pagination
- Ticket detail view (read-only)
- Attachment upload, download, and soft-delete
- Ownership verification (requesters can only access their own tickets)
- Zen Green Theme with reusable components
- Responsive design (desktop, tablet, mobile)

### Excluded
- Real authentication (login, passwords, sessions, tokens)
- IT Staff workflow (dashboard, queue, assignment)
- Public comments, internal notes, and actions taken
- Status changes beyond the initial "New" status
- Admin functions (user management, reference data)

---

## 4. Functional Requirements

**FR-01:** The system must allow the user to select a Development Requester from a list of active requesters.

**FR-02:** The system must allow the user to create a ticket with all required fields.

**FR-03:** The system must generate a unique ticket number for each new ticket.

**FR-04:** The system must list all tickets belonging to the selected requester.

**FR-05:** The system must support search functionality on the ticket list.

**FR-06:** The system must support filtering by category and status.

**FR-07:** The system must support sorting by different fields (ticket number, creation date).

**FR-08:** The system must support pagination for the ticket list.

**FR-09:** The system must display the full details of a ticket in read-only mode.

**FR-10:** The system must allow uploading attachments to an existing ticket.

**FR-11:** The system must allow soft-deletion of attachments with metadata retention.

**FR-12:** The system must verify ownership for every ticket and attachment access.

---

## 5. Business Rules

**BR-01:** The ticket number is generated by the backend and must be unique. Format: TK-YYYY-NNN.

**BR-02:** A new ticket begins with the status "NEW".

**BR-03:** The Development Requester selector is for testing only and is not real authentication.

**BR-04:** A requester can only view and manage their own tickets.

**BR-05:** Required fields for ticket creation: Category, Related System, Summary, Description.

**BR-06:** The Description field must contain at least 10 characters.

**BR-07:** Allowed attachment formats: PDF, PNG, JPG, JPEG, DOC, DOCX.

**BR-08:** Maximum attachment size: 5MB.

**BR-09:** Attachment deletion is a soft-delete (isDeleted flag set to true, metadata retained).

**BR-10:** Inactive requesters do not appear in the Development Requester selector.

**BR-11:** The Submit button is disabled during form processing (busy state).

**BR-12:** System-generated fields (Ticket Number, Ticket Date, Requester) are read-only.

## 6. UI Specification Summary

### Zen Green Theme
| Token | Hex | Usage |
|-------|-----|-------|
| Primary Green | #006B3C | App header, primary actions |
| Secondary Green | #0B7A46 | Active tabs, links, hover states |
| Pale Green | #EAF6EF | Selected items, success sections |
| Page Background | #F5F7F6 | Main application background |
| Surface | #FFFFFF | Cards and forms |
| Text | #2C3E35 | Main text (dark charcoal-green) |
| Error | #D32F2F | Error messages and borders |
| Warning | #FFA000 | Warning badges |

### Screens
1. **Development Requester Selection:** Dropdown with active requesters, explanatory text, Continue button, loading/empty/error states.
2. **Create Ticket:** All ticket fields with validation, system fields read-only, attachment upload.
3. **My Tickets:** Search bar, filters, sort options, pagination, ticket table with badges.
4. **Ticket Detail:** Read-only ticket information, attachment list with download/delete actions.

### Component Rules
- Labels appear above controls with consistent font weight.
- Required fields show a red asterisk (*).
- Inputs use consistent height (40px).
- Validation messages appear immediately below the associated field.
- The Submit button shows a busy state and is disabled while processing.
- Focus indicators remain visible for keyboard users.

## 7. Data Changes

### Database Models
| Model | Fields |
|-------|--------|
| **Requester** | id, name, email, isActive, createdAt, updatedAt |
| **Category** | id, name, description, isActive, createdAt, updatedAt |
| **System** | id, name, description, isActive, createdAt, updatedAt |
| **Ticket** | id, ticketNumber, ticketDate, requesterId, categoryId, systemId, summary, requestedPriority, itPriority, currentStatus, description, createdAt, updatedAt |
| **Attachment** | id, ticketId, requesterId, fileName, fileType, fileSize, filePath, uploadDate, isDeleted, deletedAt, deletionReason, createdAt, updatedAt |

### Relationships
- Requester 1→N Tickets
- Category 1→N Tickets
- System 1→N Tickets
- Ticket 1→N Attachments

### Enums
- **RequestedPriority:** LOW, MEDIUM, HIGH, URGENT
- **ITPriority:** LOW, MEDIUM, HIGH, CRITICAL
- **TicketStatus:** NEW, IN_PROGRESS, RESOLVED, CLOSED

## 8. API Contract

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | /api/requesters | List active requesters |
| GET | /api/categories | List active categories |
| GET | /api/systems | List active systems |
| POST | /api/tickets | Create a new ticket |
| GET | /api/tickets | List requester's tickets (search/filter/sort/paginate) |
| GET | /api/tickets/:id | Get ticket details (with ownership check) |
| POST | /api/tickets/:id/attachments | Upload attachment (multipart/form-data) |
| GET | /api/attachments/:id/download | Download attachment (with ownership check) |
| DELETE | /api/attachments/:id | Soft-delete attachment (with ownership check) |

## 9. Acceptance Criteria

**AC-01:** Given valid ticket data, when the requester submits the form, then a ticket is saved and the official ticket number is displayed.

**AC-02:** Given no Development Requester is selected, when the user attempts to open My Tickets, then the Requester Selection screen is shown.

**AC-03:** Given Requester B is selected, when a ticket belonging to Requester A is requested, then the ticket data is not returned (403/404 error).

**AC-04:** Given a ticket is created, when the requester views My Tickets, then the ticket appears in the list.

**AC-05:** Given the Summary field is empty, when the form is submitted, then an error message appears below the field.

**AC-06:** Given a valid attachment is uploaded, when the upload completes, then the attachment is saved and appears in the list.

**AC-07:** Given an attachment has been soft-deleted, when a download is attempted, then an error is returned.

**AC-08:** Given a different requester is selected, when listing tickets, then only that requester's tickets appear.

**AC-09:** Given a search term is entered, when the search is executed, then only tickets containing the term appear.

**AC-10:** Given pagination is active, when a page is changed, then the correct results appear.

## 11. Assumptions and Decisions

- Ticket number format is TK-YYYY-NNN (e.g., TK-2026-001).
- Pagination starts at page 1.
- Files are stored locally (no cloud storage).
- The ticket date is automatically set to the creation date.
- Soft-delete is used instead of hard delete for attachments.
- The Development Requester selection is for testing only and will be replaced by real authentication in Lab 3.
